# Salesforce Firmographic Intelligence UX Runbook

## Scope

This runbook promotes the validated GPT firmographic Data Cloud layer into a
Salesforce-facing validation and Account UX surface.

The original live reports were in `Private Reports`, so they were suitable for
operator validation but not for durable delivery. They have been cloned into the
`Pulse360 Account Intelligence Validation` report folder and retrieved into
source. Folder sharing still needs an admin/UI step because the Folder API kept
the folder `AccessType` as `Hidden` even after a successful update request.

## Prerequisites

- Org alias: `pulse360-agent-target`.
- Data Cloud streams refreshed successfully.
- The five Pulse360 DMOs are queryable and related to Account through
  `source_account_id__c -> Account.Id`.
- Databricks gold export counts have been validated.

## Target Folder

Create or select a shared report folder:

```text
Pulse360 Account Intelligence Validation
```

Folder access:

- Pulse360 Account Intelligence users: Viewer.
- Pulse360 data stewards/admins: Manager.

## Report Promotion Steps

For each report listed in
`config/salesforce/firmographic-intelligence-reports.csv`, the completed
promotion path is:

1. Clone the current private report using `source_report_id`.
2. Save it into `Pulse360 Account Intelligence Validation`.
3. Record the promoted report Id and developer name in the CSV.
4. Confirm report type uses Account with the relevant Pulse360 DMO.
5. Confirm the Account Id or Account Name column renders as a Salesforce record
   link.
6. Confirm no filters suppress rows unless a control-specific filter is
   documented.
7. Run the report and compare row count with `row_count_expectation`.

## Source Retrieval

After reports and dashboard are in the shared folder, retrieve them into source.
The promoted report developer names currently include Salesforce-generated
suffixes:

```bash
sf project retrieve start \
  --target-org pulse360-agent-target \
  --metadata "ReportFolder:Pulse360_Account_Intelligence_Validation" \
  --metadata "Report:Pulse360_Account_Intelligence_Validation/Account_and_Firmographic_iIW1" \
  --metadata "Report:Pulse360_Account_Intelligence_Validation/Account_and_Evidence_4W81" \
  --metadata "Report:Pulse360_Account_Intelligence_Validation/Account_and_Classification_qlX1" \
  --metadata "Report:Pulse360_Account_Intelligence_Validation/Account_and_Corporate_Linkage_U4F1" \
  --metadata "Report:Pulse360_Account_Intelligence_Validation/Account_and_Sovereign_Identifier_NOY1" \
  --metadata "DashboardFolder:Pulse360_Account_Intelligence_Validation" \
  --metadata "Dashboard:Pulse360_Account_Intelligence_Validation/zZUAzaLhrPFnOpTDCJvUEUvPEQIohz"
```

If folder or report developer names differ in a future org, use the names
produced by Salesforce after the clone or Save As step.

The dashboard developer name was generated by Salesforce when the dashboard was
created in the org. Keep that full name unless the org supports a clean Save As
or rename to a stable developer name and the retrieved metadata validates after
the change.

## Folder Sharing

The retrieved folder metadata intentionally excludes user-specific
`folderShares`. Configure sharing in the target org:

- Pulse360 Account Intelligence users: Viewer.
- Pulse360 data stewards/admins: Manager.

Do not commit user-specific email or username folder shares to source.

## Account Page Surfacing

Use the existing Account record page as the initial surfacing point. The target
shape is a read-only Firmographic Intelligence section that shows:

- Legal/trade name, jurisdiction, profile confidence, and latest verification.
- Business description and category.
- Latest investor/financial summaries only where source-backed.
- Classification and corporate linkage related rows.
- Evidence/provenance with source URL, source type, excerpt, confidence,
  retrieved timestamp, and model version.

Keep stewardship controls outside this read-only section.

Use `config/salesforce/account-firmographic-intelligence-surface.yaml` as the
source checklist for fields, regions, and editability. If the target org cannot
source-deploy the chosen Data Cloud related-list or embedded-report components,
record the placement as a runbook-controlled setup step rather than hard-coding
generated relationship field names into LWC or Apex.
