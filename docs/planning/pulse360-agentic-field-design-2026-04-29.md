# Pulse360 Agentic Field Design

Date: 2026-04-29

## Decision

Pulse360 should use Agentforce for agentic interpretation fields, not as the
primary calculator for deterministic account intelligence fields.

The design split is:

1. Databricks and Data Cloud decide facts, scores, keys, eligibility, lineage,
   freshness, and confidence components.
2. Agentforce reads those governed facts and creates explanations,
   recommendations, objections, seller/steward next steps, and action packages.
3. Salesforce stores only the approved or surfaced agentic output with audit,
   prompt, model, source, and approval metadata.

## Why

Agentforce is strong where the output needs judgment, synthesis, and
conversation. It is weaker as the source of record for repeatable scoring,
identity, eligibility, and activation state because those outputs must be
deterministic, testable, lineage-backed, and safe for downstream automation.

Using Agentforce for companion fields gives Pulse360 a stronger product story
without making the data layer fuzzy:

- deterministic intelligence remains reproducible
- agentic recommendations remain explainable and reviewable
- CRM fields can distinguish facts from interpretations
- steward and seller actions can preserve human approval gates
- audit can show which model/prompt/source set produced a recommendation

## Field Ownership Rules

### Deterministic Fields

These must remain owned by Databricks, Data Cloud, or deterministic Apex logic.
Agentforce may explain them, but must not be the source of truth.

| Field family | Examples | Owner |
| --- | --- | --- |
| Identity and keys | `source_account_id`, `resolved_entity_id`, `crm_activation_key`, `unified_profile_id` | Databricks/Data Cloud |
| Scores and bands | `confidence_score`, `duplicate_confidence`, `hierarchy_confidence`, `health_score`, `validity_score_external` | Databricks/Data Cloud |
| Eligibility and routing | `activation_eligible_flag`, `activation_block_reasons`, `review_priority`, `coverage_gap_flag` | Databricks/Data Cloud |
| Operational state | `downstream_update_status`, `audit_event_id`, `last_synced_timestamp`, `enrichment_run_id` | Salesforce/Data Cloud/Apex |
| Evidence payloads | `source_refs`, `confidence_components`, `hierarchy_payload`, `attribute_validity_payload` | Databricks/Data Cloud |

### Agentic Companion Fields

These can be generated by Agentforce, provided they are grounded in the
deterministic fields and stored with provenance.

| Field | Purpose |
| --- | --- |
| `Agent_Recommendation__c` | Human-readable recommended seller or steward move |
| `Agent_Rationale__c` | Why the agent recommended the move |
| `Agent_Evidence_Summary__c` | Grounded summary of the evidence used |
| `Agent_Risk_Flags__c` | Objections, uncertainties, and risk warnings |
| `Agent_Confidence_Explanation__c` | Explanation of confidence components, not the score itself |
| `Agent_Next_Best_Action__c` | Ranked next action or action package |
| `Agent_Output_Status__c` | Draft, surfaced, accepted, rejected, superseded, or expired |
| `Agent_Last_Run_At__c` | Timestamp of the agentic interpretation run |
| `Agent_Model_Id__c` | Runtime model identifier |
| `Agent_Prompt_Version__c` | Prompt or topic version used |
| `Agent_Source_Refs__c` | JSON list of source IDs used by the agent |
| `Agent_Run_Id__c` | Correlation ID for audit and troubleshooting |

## Runtime Pattern

Agentforce should be invoked through explicit actions rather than hidden page
load side effects:

1. User opens Account or Governance Case surface.
2. LWC/Apex loads deterministic account, Data Cloud, and governance evidence.
3. User or workflow invokes an Agentforce action such as:
   - `Generate seller recommendation`
   - `Explain confidence`
   - `Prepare steward decision brief`
   - `Draft next-best-action package`
4. Agentforce returns a structured response with:
   - recommendation
   - rationale
   - evidence summary
   - risk flags
   - source references
   - model/prompt/run metadata
5. Low-risk outputs may be displayed immediately.
6. Persisted agentic fields require explicit save/accept action.
7. Mutating business actions continue to require confirmation or approval.

## Acceptance Criteria

- No deterministic field is newly calculated by Agentforce.
- Agentforce output is clearly labeled as interpretation, recommendation, or
  action packaging.
- Every persisted agentic field stores model, prompt, run, timestamp, and source
  reference metadata.
- Agentforce outputs can be regenerated without corrupting the underlying
  deterministic intelligence state.
- Users can reject or supersede agentic outputs without changing source facts.
- Tests prove that missing evidence fails closed and does not create misleading
  recommendations.
- The UI distinguishes facts, agentic interpretation, and approved decisions.

## Implementation Slices

1. Contract slice: update Data Cloud -> Salesforce/Agentforce contract with
   field ownership and companion-field rules.
2. Metadata slice: add agentic companion fields to the relevant Account and/or
   Governance Case source objects only after final field targets are selected.
3. Action slice: create Agentforce/Apex action for generating an agentic field
   packet from existing deterministic context.
4. UI slice: render agentic fields in Account and Governance surfaces as
   interpretation cards, with clear provenance and accept/reject controls.
5. Validation slice: prove deterministic fields are unchanged by agentic
   regeneration and prove persisted outputs carry full audit metadata.

## Open Design Questions

- Should agentic companion fields live on `Account`, `Governance_Case__c`, or a
  separate `Pulse360_Agentic_Insight__c` object?
- Which outputs should be persisted by default versus displayed ephemerally?
- Should seller and steward agentic fields share a common schema or use
  workflow-specific field sets?
- What expiration window should apply to agentic recommendations when Data
  Cloud freshness changes?
